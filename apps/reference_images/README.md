# Board-only finite image reference demos

Build using `CXX=<cross-g++> HBN_ROOT=<staged>/usr/hobot apps/reference_images/build.sh` from repo root. If using split BSP staging, set `HBN_HEADERS` (directory containing `hbn_api.h`) and `HBN_SYS_LIB` (system usr/lib) as well. The BSP rootfs includes `/usr/bin/flock`. Deploy `dist/bin/reference_images_demo`, `dist/nv12_demo`, `dist/jpeg_demo` preserving bin/ layout. On the board run `dist/nv12_demo` **or** `dist/jpeg_demo` with `--camera-mask 0xF --frames-per-camera 10 --base-port 5610 --wait-timeout-ms 10000`. All four selected ports are listened to concurrently, one port per camera. No camera/codec starts before a valid OCTL START. No image work runs after the selected client disconnects; count is *successful TCP sends*, not proof of host receipt. Timeout/partial delivery exits nonzero. Board clock timestamps are not synchronized host time.

The board binary (including direct invocation) takes the same nonblocking advisory lock `/run/lock/orbvi-reference-camera-owner.lock` using `flock`, held until all four camera worker threads exit and the process closes it. Failure to acquire/open the lock fails closed. Launchers choose the mode; direct binary invocation also enforces the lock. This lock protects only programs that use it: existing RTSP cam_demo and legacy UVC do **not** participate. Stop all old RTSP/UVC camera-owning processes before starting either reference demo; this cannot automatically protect against an old UVC process. Never run both demos with other camera owners. The codec configuration follows the BSP `sample_codec.c` JPEG example and must be verified on hardware. Host/cross-build tests alone do not establish board camera/codec correctness.

Host-only tests: `HBN_HEADERS=<X5 public headers> apps/reference_images/test.sh`. JPEG test uses mocked media-codec functions; it does not verify physical X5 behavior.
